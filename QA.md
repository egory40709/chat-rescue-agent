# Проверка Chat Rescue Agent 1.1.0 — 03.11.2026

## Новый основной сценарий: уже открытая сессия

**28/28 автоматических проверок прошли**, без пропусков на macOS arm64,
Node.js 24.15.0, Playwright 1.64.0. Существующие 14 проверок режима отдельного профиля
сохранены; добавлены 14 проверок подключения к текущему браузеру.

Проверено в реальном Chromium и по настоящему локальному CDP:

- Обычная сессия браузера заранее содержит искусственную авторизационную cookie.
  Сервер тестовой страницы требует её; без неё показывает вход. Инструмент не
  читает cookies: его рабочая вкладка наследует существующий браузерный контекст.
- `open_export_session` сразу начинает поиск, сохраняет два чата и собирает ZIP.
  Нет дополнительного `start_export`, `continue` или подтверждения `user_ready`.
- Производственная команда `node agent.mjs export` запускает отдельный worker и
  действительно завершает сохранение текущего чата без TTY и ручного продолжения.
- Подключение через WebSocket из DevToolsActivePort не зависит от `/json/version`.
  Разрешены только loopback-адреса; посторонние адреса и credentials отклоняются.
- Исходная вкладка, её URL и браузер остаются открытыми после экспорта и после
  остановки активной задачи. Закрываются только рабочая вкладка и CDP-соединение.
- Отсутствующая вкладка и окно входа не вызывают fallback в отдельный пустой профиль.
  При signin-модальном окне в архив не записывается фиктивный успешный диалог.
- Медленный клиентский рендеринг ожидается до появления истории: временно пустая
  страница не принимается за потерянный вход. Это проверено отдельной задержанной страницей.
- При нескольких вкладках выбирается активная, а неоднозначность возвращается
  как `source_tab_required`, без угадывания аккаунта.
- Для macOS нативный адаптер проверен через моделируемый мост и настоящий DOM
  Chromium: сначала проверяется разрешение, затем создаётся рабочая вкладка в
  выбранном окне. При запрете новая вкладка не создаётся. JXA-код компилируется
  штатным `osacompile` без доступа к браузеру пользователя.

Браузер в этих тестах работает offline. Страницы, аккаунт и cookie искусственные.
Это подтверждает повторное использование сессии, но не чтение корпоративных данных.

## Границы подтверждения

Реальный системный диалог Chrome 144+ о подключении и реальная автоматизация
обычного Chrome через Apple Events не проходились на приватном аккаунте сотрудника.
Штатный механизм текущей сессии сверён с официальной документацией Chrome:
https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session

Подключение может потребовать разрешения управления браузером. Настройки безопасности
не переключаются автоматически. Сессия внутри настольного приложения ChatGPT/Claude
не заявляется как поддержанная браузерная сессия. Windows/Edge отдельно не проверялись.

Живой экспорт корпоративных переписок, полнота истории, все архивные/проектные
списки и все вложения по-прежнему не подтверждены. Режим `complete` относится к
выбранной очереди. Вложения, изображения, Canvas/Artifacts, скрытые блоки и другие
ветки нужно сохранять отдельно.

Ниже сохранён протокол предыдущего режима 1.0.0; в 1.1 он выбирается только явно
через `--isolated` или `connection=isolated`.

# Проверка Chat Rescue Agent 1.0.0 — 03.11.2026

## Что действительно проверено

macOS arm64, Node.js 24.15.0, Playwright 1.64.0, официальный MCP SDK 1.32.2.
**14 автоматических проверок прошли**; они используют настоящий SDK-клиент,
настоящий stdio-сервер, отдельные процессы и реальный Chromium.

1. MCP handshake, 9 tools и prompt `export_my_chats`.
2. Открытие браузера без автоматического чтения до `user_ready=true`.
3. Один `start_export` сам ищет ссылки, сохраняет два диалога и собирает ZIP в фоне.
4. Повторный запуск проверяет SHA-256 и не делает новые GET сохранённых диалогов.
5. Закрытие MCP и новый клиент восстанавливают архив и продолжение очереди.
6. HTTP 403 останавливает очередь без повтора и чтения следующей ссылки;
   сохранённый результат можно упаковать отдельно.
7. Claude работает через тот же механизм; чужие URL отклоняются до запуска.
8. Потеря MCP-процесса во время выгрузки сохраняет очередь; новый клиент дочитывает её.
9. Detached CLI worker управляется настоящими командами `continue/status/pack/close`
   без TTY и ручного ввода в терминале.
10. Лимит чтений и намеренная остановка имеют разные `stop_reason`; resume работает.
11. Живой lock и нераспознанный lock не удаляются.
12. Lock от действительно завершённого процесса сохраняется и заменяется безопасно.
13. Два одновременных старта используют один job и не дублируют чтение.
14. Текст переписок не попадает в stdout/stderr или метаданные MCP-инструментов.

В тестах сайты заменены синтетическими ответами, а браузер работает offline.
Производственные entry point не включают тестовые подмены. Это проверка механики,
а не подтверждение полноты корпоративной истории или актуальности всех DOM-селекторов.

## Производственный входной путь

Отдельно запущен именно `mcp.mjs` без тестовой фабрики. Настоящий SDK-клиент:

- обнаружил 9 tools;
- открыл выделенный обычный Chrome через `open_export_session`;
- получил `awaiting_login` и HTTP 200 главной ChatGPT;
- получил `login_verified=false`, текущего чата нет;
- закрыл собственную сессию; `browser_closed=true`, сохранено 0 чатов.

Пароли, cookies и основной браузерный профиль сотрудника не использовались.
Сотрудник ранее сообщил, что сейчас не может войти; приглашение ко входу не повторялось.

## Артефакты

Настоящий ZIP экспорта из MCP-теста независимо прочитан Python `zipfile`:
CRC, UTF-8, два JSON, два Markdown, индекс, manifest и EXPORT-ISSUES корректны.
Служебные команды, run.json и профили в ZIP отсутствуют. Модули проходят
`node --check`, инструмент — ESLint. Сборка включает только явный список исходников
и не зависит от проекта AI Product Design Studio или браузерного расширения.

## Что не подтверждено

Живое чтение корпоративных переписок ChatGPT Business/Team и Claude, полнота
истории, все архивные/проектные списки, Windows/Edge и ручное подключение в конкретном
AI-клиенте пока не проверены. Команды подключения сверены с официальными документами;
протокол проверен отдельным настоящим SDK-клиентом.

Сохраняется прочитанный текст отображённой ветки. Вложения, изображения,
Canvas/Artifacts, скрытые блоки и другие ветки нужно сохранять отдельно.
Никаких paid AI POST, публикаций и отправки сообщений в ходе тестов не было.
